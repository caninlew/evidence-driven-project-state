# Strategy

## 1. 项目定义

`Evidence-Driven Project State` 不是一个通用待办事项工具，也不是一个建筑师专用提示词合集。

更准确的定义是：

**一个基于证据、状态和版本控制的项目整理框架，并以建筑项目作为第一优先落地场景。**

它解决的是复杂项目里的“上下文治理”问题，而不是简单任务派发问题。

## 2. 要解决的根问题

复杂项目最常见的失控点，不是执行动作本身，而是以下几类上下文混乱：

- 来源很多，但缺少登记
- 会议纪要、邮件、顾问意见、口头反馈混在一起
- “被讨论过”被误写成“已确认”
- 冲突来源被悄悄抹平
- 新人接手时，只能靠口头交接补上下文
- 后续方案研究和测试，建立在未经清洗的前提上

这类问题在建筑、咨询、产品、研究、审批协同中都非常常见。

## 3. 类别定位

如果按 GitHub 上已有项目类型划分，这个项目最接近以下几类能力的交叉：

- ADR / 决策记录
- markdown-native project management
- agent workflow governance
- evidence-aware documentation systems

但它并不等于其中任何一个。

它的独特位置是：

**在“原始资料治理”与“决策/研究执行”之间，建立一个可追溯的项目状态层。**

这就是它的品类价值。

## 4. 战略楔子

最适合的切入点，不是先说“这是通用项目管理框架”，而是：

**先作为建筑与设计团队的高上下文项目整理框架进入，再向其他知识密集型领域扩张。**

原因很直接：

1. 建筑项目的痛点更尖锐，更容易体现价值
2. 建筑场景对“来源、权限、冲突、未确认信息”的要求更高
3. 在高要求场景打磨过的方法，更容易向咨询、研究、产品需求治理扩展

也就是说：

- **首发叙事**：architecture-first
- **产品本质**：domain-extensible

## 5. GitHub 上应采用的项目叙事

建议对外统一为三层表达：

### 5.1 Category

Evidence-driven project-state framework

### 5.2 Wedge

Originally optimized for architecture and design workflows

### 5.3 Expansion

Adaptable to consulting, product, research, and other multi-source projects

这样做的好处是：

- 保留你当前最强的真实场景
- 不把项目锁死在“建筑师专用”
- 让外部使用者更容易理解是否适配自己的场景

## 6. 核心差异化

这个项目的核心差异化，不是“会生成文档”，而是以下几件事同时成立：

1. **来源先于解释**
2. **未确认信息不得升级为事实**
3. **冲突必须显式保留**
4. **建议与决策严格分层**
5. **研究链路不能跳过状态层**
6. **版本新增优先于覆盖修改**

这使它更像一个“项目上下文治理系统”，而不是普通提示词包。

## 7. 对标策略

对标时不要说“我们是另一个 task manager”。

更合适的对标口径是：

- 比 ADR 更前置：不仅记最终决策，还治理决策前的原始资料和冲突状态
- 比 markdown task board 更深：不仅管任务，还管事实、证据、来源、冲突和开放问题
- 比普通 agent workflow 更稳：不是让 agent 自由发挥，而是把 agent 约束在明确的治理纪律里

## 8. 开源版推荐结构

推荐采用：

```text
core framework
  + domain packs
  + examples
  + release docs
```

其中：

- `core` 负责方法论和通用规则
- `domain packs` 负责建筑、咨询、产品等垂直扩展
- `examples` 负责可理解性
- `release docs` 负责可信度与采用门槛

## 9. 发布到 GitHub 前必须补齐的部分

从“内部可用”到“公开可信”，最需要补的不是更多 skill，而是：

1. 清晰命名
2. 开源 README
3. 竞争参照说明
4. 适用边界说明
5. 贡献规范
6. 发布清单
7. 至少 2 到 3 个跨领域样例

## 10. 一句话战略结论

这个项目最好的公开定位不是：

“建筑师项目管理 skill”

而是：

**一个以建筑领域为首发场景的、基于证据与状态治理的通用项目整理框架。**
