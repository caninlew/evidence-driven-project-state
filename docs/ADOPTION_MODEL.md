# Adoption Model

## 1. 推荐采用方式

这个项目最适合采用“轻接入、强边界、逐步放量”的方式，而不是一次性要求团队彻底迁移。

建议分三步推进。

## 2. 第一步：单项目试点

选择一个高信息密度、材料相对完整的项目，建立单独项目根目录。

目标不是立刻全自动，而是先验证三件事：

1. 原始资料是否能被稳定整理成状态层
2. 冲突与开放问题是否能被显式暴露
3. 新成员是否能比过去更快接手

推荐输入：

- 任务书
- 会议纪要
- 顾问反馈
- 邮件摘录
- 图纸说明

此阶段先用：

- `architect-project-state`

## 3. 第二步：从状态层进入研究层

当状态层稳定后，再引入：

- `architect-method-lens`
- `design-test-framework-rounds`

目的不是直接生成方案，而是：

- 把研究建立在清洗后的前提上
- 把方法迁移建立在可追溯上下文上
- 把测试框架与最终定稿明确区分

## 4. 第三步：增强证据检索能力

只有当团队确实需要本地知识检索层时，再接入：

- `architect-wiki-builder`

这一步是增强项，不应成为首轮采用门槛。

## 5. 适合采用的团队特征

优先推荐给：

- 材料来源多
- 参与角色多
- 决策责任链长
- 经常换人接手
- 需要长期保存上下文

如果团队目前只是需要：

- 任务派发
- 截止时间提醒
- 简单看板

那应优先使用标准 PM 工具，而不是先上这个框架。

## 6. 采用成功的判断标准

如果采用成功，通常会出现这些变化：

1. 会议纪要不再直接等同于已确认结论
2. 冲突项开始被显式管理，而不是靠口头记忆
3. 项目接手速度明显提升
4. 方案研究前提更稳定
5. 后续返工中，“前提不清”类问题减少

## 7. 失败信号

以下情况说明采用方式不对：

1. 把它当作自动出结论工具
2. 不指定项目边界，直接让 agent 扫大量混杂目录
3. 在没有状态层的情况下直接进入方法研究或测试框架
4. 把未确认信息直接当作项目事实继续 downstream 使用

## 8. 推荐组织方式

项目目录建议保持单项目边界：

```text
project-root/
├─ 01_sources/
├─ 02_state/
└─ 03_outputs/
```

名称不是关键，边界才是关键。

## 9. 一句话采用建议

先用它把一个项目的原始资料整理成“项目状态层”，不要一上来就把它当作全自动项目管理系统。
